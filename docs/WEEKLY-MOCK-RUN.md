# Weekly mock run (runbook)

Every Friday a fresh session runs the whole site as every role, on a seeded local
copy, at desktop and phone width, and reports **only what is new or broken** since
the last run. It is issue #1441, part of the club launch gate (#1442). Before club
launch it also runs once on demand as the final gate.

This file is written so a session with no other context can follow it alone.

## Ground rules

- **Synthetic data only.** Seeded database plus the repo's journey and seed helpers.
  Never production data, real people, real email, secrets or payment credentials,
  in the run, the screenshots or the report.
- **Local only.** Production build on this machine. Email goes to the local catcher
  (`RESEND_API_URL=http://127.0.0.1:3999`); Square uses the fictitious CI values, so
  no real payment can happen.
- **New or broken only.** Compare with the previous report. Do not repeat an
  earlier finding unless it got worse; list it under "Still open" in one line.
  Say which earlier findings are now fixed.
- **Draft issues are not created.** They go at the end of the report for Caleb to
  approve. Do not open issues, do not merge, do not deploy.
- **An independent reviewer reproduces the top findings** before they are reported.
- **One PR, docs only**, ready for review, target `main`, using the repository PR
  template. Then one short plain-language comment on #1441 with the headline and
  the PR link, ending with `_Generated by [Claude Code](https://claude.ai/code)_`.
- Keep the report and the comment short and plain: Caleb is not a developer.

## 1. Read first

1. `CLAUDE.md`, `AGENTS.md`, `docs/SITE-RULES.md`.
2. The previous report: the newest `docs/MOCK-RUN-QA-*.md`, and its
   `docs/mock-run-qa/<date>/page-check-baseline.txt`.
3. Issue #1441 and the club launch gate #1442
   (`gh api repos/DurantTL/IMSDA-Events/issues/1441`, `.../1442`, plus `/comments`).
4. What merged since the last run: `git log --oneline --merges -60` and the PR
   titles. These are the week's "recent work" to test by hand (step 5).

## 2. Database and build (about 15 minutes)

```bash
sudo service postgresql start
# First time only: role and database from .env.example's DATABASE_URL
sudo -u postgres psql -c "CREATE ROLE imsda LOGIN PASSWORD 'imsda_dev' CREATEDB;"
sudo -u postgres createdb -O imsda imsda_events
cp .env.example .env            # if missing
export DATABASE_URL='postgresql://imsda:imsda_dev@localhost:5432/imsda_events?schema=public'
npm run db:deploy && npm run db:seed && npm run club-forms:sync && npm run lodging:sync \
  && npm run form-templates:sync && npm run event-content:sync
NODE_OPTIONS=--max-old-space-size=8192 npm run build      # run in the background
```

## 3. Start the apps and run the repo's browser suites

Start the built app on port 3000 and the Security-check app on port 3002 with the
CI values from `.github/workflows/ci.yml` ("Start the built apps"). A copy of that
block is in [`mock-run-qa/tools/start-apps.sh.txt`](mock-run-qa/tools/start-apps.sh.txt)
(`bash start-apps.sh <log folder>`). Wait until `curl -fsS http://localhost:3000/`
answers.

Then run these **one after another** (each starts the fake mail server on 3999):

| Check | Command | Covers |
| --- | --- | --- |
| Club journeys | `JOURNEY_SHARD=desktop npm run test:club-journeys`, then `phone` | Club director and Area Coordinator launch journeys, desktop and phone |
| Event journeys | `JOURNEY_SHARD=desktop npm run test:event-journeys`, then `phone` (with `JOURNEY_TURNSTILE_BASE_URL=http://localhost:3002`) | Attendee (account, register, promo, card, cancel), event staff (template, publish, form test, attendee list, check-in, scheduled email) |
| Keep your place (B17) | `npm run test:keep-place` | Load shift and scroll position at 1280 and 390 |
| Translation | `JOURNEY_BROWSERS=chromium npm run test:translation-sim` | T1 (only Chromium is installed in cloud sessions) |
| Mobile layout | `MOBILE_LAYOUT_BROWSER=/opt/pw-browsers/chromium MOBILE_LAYOUT_OUT_DIR=<scratchpad>/mobile-layout MANAGE_LINK_DERIVATION_SECRET=ci-only-manage-link-derivation-secret-0000000 npm run test:mobile-layout` | 231 pages at 360, 390, 768 and 1024 px (about 70 minutes; start it early) |
| Privacy browsers (optional) | needs the app restarted with `EMBED_ALLOWED_ORIGINS` (see `.github/workflows/browser-privacy.yml`), then `PRIVACY_BROWSERS=chromium npm run test:privacy-browsers` | T2, T3 |

Cloud-session gotchas:
- Playwright is preinstalled at `/opt/node-tools/node_modules`. The journey suites
  find it. The mobile audit imports `playwright-core` as a module, so link it for
  the run: `ln -s /opt/node-tools/node_modules/playwright-core node_modules/playwright-core`
  (remove the link afterwards; never add it to `package.json`).
- Never run two builds at once. The suites may run while the walk (step 4) runs,
  but not two suites at once (they share the mail port).

## 4. Walk every role (both widths)

Copy [`mock-run-qa/tools/role-walk.ts.txt`](mock-run-qa/tools/role-walk.ts.txt) to
your scratchpad as `role-walk.ts` and run it from the repo root:

```bash
NODE_PATH=$PWD/node_modules:/opt/node-tools/node_modules:$NODE_PATH \
DATABASE_URL=... WALK_KEEP=1 \
npx tsx --require ./scripts/support/allow-server-only.cjs <scratchpad>/role-walk.ts
```

It seeds its own synthetic club, director, Area Coordinator, attendee and a
Clubs Administrator (`mockrun.clubsadmin@imsda-events.test`, with a sign-in
credential: a staff session without one is treated as signed out), mints
sessions, and visits each role's pages at **1280 px and 390 px**:

| Role | Pages |
| --- | --- |
| Public visitor | home, events, an event page, calendar (month and upcoming), club finder, club forms, sign-in pages, recover registration, register, calendar embed |
| Attendee | account, registrations, profile, help, and a staff page (expects the "no access" page) |
| Club director | club home, roster, forms, events, honors, class tracking, Monthly Records, orders, health, club info, help |
| Area Coordinator | overview, records, events, applications, points, team approvals, a club's view, help |
| Event staff | registration, finance, check-in and communications staff (seeded `@imsda-events.test` users) on their pages for Women's Retreat 2026 |
| Clubs Administrator | club administration, leaders, invites, monthly records, summary, applications, transfers, club forms, supplies, honors, a club, and System pages (expects a clear "no access") |
| System administrator | system home, email, system report, settings, calendar admin, people, templates, event setup, readiness, site content, organizations, clubs |

For each page it saves a full-page screenshot and records status, redirects, the
h1, sideways scroll, console and page errors, 5xx responses, and the shared
site-rule page checks (`checkPage` from `scripts/support/site-rule-checks.ts`).

Add pages when new pages ship. Use `WALK_ROLES=clubsadmin` (comma list) to rerun
one role.

## 5. Test the week's new work by hand

For each feature merged since the last run, write a short Playwright check (start
from [`mock-run-qa/tools/recent-features.ts.txt`](mock-run-qa/tools/recent-features.ts.txt),
which covers Act as Area Coordinator, Monthly Records naming and Calendar admin
filters) and run it at both widths. Try what a person would actually do: click
through, go Back, reload a filtered link, stop what you started.

## 6. Sort the results

1. **Suites:** any failure in a step-3 suite is a finding (unless it is a known
   bug the suite already lists).
2. **Walk:** look at pages with a non-200 status, an unexpected redirect, sideways
   scroll, more or fewer than one h1, errors, or a 5xx.
3. **Page checks:** compare with the previous `page-check-baseline.txt`. Only a
   flag that is **not** in the baseline needs a look. Many flags come from the
   checker's strict word lists on pages it is not tuned for (system administrator
   pages are not yet in the browser journeys, #1439 round 3): check the page before
   calling it broken. A flag caused by the test data (for example a count changing
   because another suite added clubs at the same time) is not a finding.
4. **Earlier findings:** for each item in the previous report's draft issues and
   "Still open" list, check whether it is fixed (code at the cited file:line, plus
   a browser look for anything visible).
5. Spot-check two or three key screenshots yourself; hand big screenshot folders
   to the explorer agent.

## 7. Independent reproduction

Before writing the report, give a read-only reviewer agent the top findings (steps,
widths, cited file:line) and how to mint sessions (`scripts/support/browser-journeys.ts`).
It reproduces each one and says REPRODUCED / NOT REPRODUCED, correcting any
file:line. Report only what it reproduced; say so for anything it could not.

## 8. Write the report

`docs/MOCK-RUN-QA-<YYYY-MM-DD>.md`, with screenshots in
`docs/mock-run-qa/<YYYY-MM-DD>/` (synthetic data only; check each image before
committing) and the new `page-check-baseline.txt` there.

Sections, in order:

1. **Header:** base commit, data, how it was run, what was not run and why.
2. **Summary for Caleb:** five to ten plain lines. How many new or broken items,
   the worst ones, and what is fixed since last time.
3. **Suite results:** one table, pass or fail per suite and width.
4. **New or broken findings,** ranked broken, then confusing, then polish. Each one:
   - role, page, width;
   - steps;
   - expected and actual;
   - file:line when found;
   - screenshot link;
   - reproduced by the reviewer (yes or no).
5. **Fixed since the last run:** IDs with the PR that fixed them.
6. **Still open from earlier:** one line each, no repeats of the full write-up.
7. **Checker flags:** what the automated checks flagged that is not a finding, and why.
8. **Draft issues** (title and body), in priority order, each sized for one build.
   Not created.

## 9. Ship

- Branch `claude/issue-1441-mock-run-<date>`, docs only, `npx eslint . --max-warnings=0`
  (fast; proves nothing else changed). Full `npm run verify` is not needed for a
  docs-only change; say so in the PR.
- PR to `main`, ready for review, repository template, label nothing. Subscribe to
  its activity.
- One comment on #1441: headline numbers, the worst two or three items, the PR
  link, and the footer.
- Clean up: stop the apps, remove the `playwright-core` link, leave the database.
