IMSDA Events: current capabilities and future possibilities

Prepared October 21, 2026 · Repository baseline 5e367b7c
Current implementation, gated capabilities, accepted design and future plans are distinguished in the text. Repository evidence does not establish the serving production state.

IMSDA Events already supports substantial event and club operations. The useful next step is to make those capabilities easier to recognize, learn and operate, while extending the existing modules where the roadmap calls for it. This guide separates what is implemented from accepted presentation work and longer-term possibilities; it does not turn future scope into a product promise.

Reading the status: “Implemented” means present in the reviewed repository. “Gated/setup” means code exists but a switch, event setup, provider or human prerequisite still matters. Neither status verifies the serving production release. “Accepted design” means the presentation direction was accepted, not built. “Planned” means tracked scope whose policy, design, timing or dependencies may still be unresolved. The companion feature-matrix.json contains the machine-readable evidence and owner links.

What people can do with the current foundations

Role Work the system supports Scope that training must preserve
Attendee or registration contact Discover events, register eligible people, manage an accessible registration, pay an eligible balance, read published event information and retrieve an owned pass. Personal access and registration authority; no staff sidebar. A group booking is not a permanent household or guardian grant.
Club director/deputy Maintain a selected club/year roster, forms and Monthly Records; register selected people for club events; use honors, orders, reports and permitted assignment/invoice views. Actual deputy/registrar/reporter grants differ. Church-billed events do not become the director’s personal payment obligation.
Area Coordinator Review currently available clubs, records and points; follow the existing narrow review links. Current club scope is all active clubs in source; ministry scoping is future work. Most club/report views are read-only. Health paths have a separate contract.
Event staff and system administrators Configure permitted events, forms/content, registrations, finance, communications and operations; system administrators manage platform settings and access. Real server permissions, System versus Event context and specialized domain guards remain authoritative. Kitchen-only staff have a dedicated narrow entry.

The accepted four-role examples refine these experiences without making them share the same administrator menu. See the role reference and navigation ownership in #1074. Later calendar, roster and event-page samples are illustrative page studies, not extra changes to System navigation.

A useful way to present the future

Teach today’s tasks first: find the correct event or club/year, understand the current state, take the permitted action and recover from an error. Present accepted workspace design as an improvement to that same job. Then show future capabilities as modules that extend an existing source of truth rather than a replacement platform.

For example, a new theme should reuse the registration and event renderers; saved views should reuse authorized query/column definitions; camp cabins should build on lodging while adding the actual camp authority model; and wallet/native access should consume an approved API instead of maintaining another enrollment or balance record. The code report and separate UltraCamp discovery report explain these boundaries in more depth.

Sequence remains #98. This guide assigns no new delivery dates, changes no role/menu contract and enables no production feature. Items not evidenced here should be marked unknown, not filled in from a competitor’s product sheet.
